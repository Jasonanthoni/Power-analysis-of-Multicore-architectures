# Power Analysis of Prefetcher and Cache Coherence Protocols in Tiled Multicore Architectures

Research Experience for Undergraduates (REU) · KLE Technological University, Hubli, Karnataka, India

---

## Overview

Modern multicore processors rely on efficient cache hierarchies, hardware prefetching mechanisms, and cache coherence protocols to improve performance while managing power consumption.

This research investigates the performance and power implications of adaptive prefetching and MESI-IN cache coherence in tiled multicore architectures using **gem5** and **McPAT**.

The project establishes a 16-core x86 baseline architecture and evaluates different architectural configurations using the PARSEC benchmark suite. Simulation statistics generated by gem5 are processed through a gem5-to-McPAT workflow to support power estimation and comparative analysis.

The repository contains the experimental configurations, simulation and analysis scripts, generated outputs, research documentation, and comparative studies developed as part of the project.

## Research Objectives

- Establish a 16-core x86 multicore simulation baseline using gem5.
- Investigate the impact of adaptive prefetching on multicore architectural behaviour.
- Study the effects of MESI-IN cache coherence on system performance and estimated power.
- Compare baseline and modified architectural configurations under consistent workloads.
- Automate the processing of gem5 simulation outputs for McPAT-based power estimation.
- Analyse the performance and power trade-offs associated with different architectural configurations.

## Experimental Setup

### Baseline Architecture

The baseline system is a 16-core x86 multicore architecture configured in gem5 with a two-level Ruby cache hierarchy and a MESI-based cache coherence configuration.

The baseline serves as the reference for evaluating the effects of adaptive prefetching and the MESI-IN configuration.

### Experimental Configurations

The study is organised around four experimental configurations.

| Configuration | Description |
|---|---|
| **Baseline** | Reference multicore architecture |
| **Baseline + Adaptive Prefetching** | Baseline architecture with adaptive prefetching enabled |
| **Baseline + MESI-IN** | Baseline architecture using the MESI-IN coherence configuration |
| **Adaptive Prefetching + MESI-IN** | Combined configuration incorporating both modifications |

The exact parameters and implementation details for each experiment are maintained in the corresponding configuration files.

### Workload Suite

The experiments use the PARSEC benchmark suite with the `simsmall` input size.

The workloads provide a range of parallel application behaviours for investigating how prefetching and cache coherence affect multicore execution.

The benchmark outputs are organised by workload and experimental configuration to support systematic comparison.

## Experimental Workflow

The project follows a simulation-to-analysis workflow.

1. **Architecture configuration:** Define the baseline and modified multicore configurations.
2. **Simulation execution:** Run the selected PARSEC workloads using gem5.
3. **Statistics collection:** Extract architectural statistics and configuration metadata.
4. **Power modelling:** Prepare the required architectural inputs and process them using McPAT.
5. **Result organisation:** Store simulation outputs and power-model artefacts in the appropriate directories.
6. **Comparative analysis:** Evaluate performance and estimated power across the experimental configurations.
7. **Documentation:** Record the methodology, observations, comparisons, and conclusions.

## Directory Guide

### `configs/`

Contains the configuration files associated with the four experimental setups.

Each subdirectory groups the relevant configuration and parameter changes for its respective architecture.

### `scripts/`

Contains the scripts used to execute experiments, automate repetitive tasks, extract simulation statistics, and process gem5 outputs for power estimation.

The directory will also document the execution commands and dependencies required by the scripts.

### `mcpat/`

Contains documentation and supporting material related to McPAT, including version information, input preparation, and the power-estimation workflow.

### `results/`

Stores the outputs generated during the experiments.

- **`performance/`** — gem5 simulation outputs, architectural statistics, configuration metadata, and other performance-related artefacts.
- **`power/`** — McPAT input XML files, generated reports, and other power-modelling artefacts.

Results are organised by experimental configuration to facilitate reproducibility and comparison.

### `analysis/`

Contains the detailed analysis of the simulation and power-modelling results.

- **`performance/`** — Performance metrics, plots, and workload-level observations.
- **`power/`** — Power estimates, component-level analysis, and relevant modelling assumptions.
- **`comparisons/`** — Cross-configuration comparisons, interpretation of results, and research conclusions.

This directory serves as the primary location for the project's detailed analytical findings.

### `docs/`

Contains supporting research documentation.

- **`architecture/`** — System architecture diagrams and experimental workflow illustrations.
- **`presentations/`** — Research presentations and project slides.
- **`reports/`** — Project reports and other research documents.

## Reproducibility

The repository is intended to support transparent and reproducible architectural experiments.

Where applicable, each experiment should be associated with:

- The relevant gem5 configuration.
- The benchmark and input size.
- The simulator version and execution parameters.
- The generated simulation statistics and configuration metadata.
- The corresponding McPAT inputs and outputs.
- The scripts and methodology used for analysis.

These artefacts help establish a traceable connection between the experimental setup, simulation outputs, power estimates, and conclusions.

Simulation results and power estimates depend on the architecture, workload, configuration parameters, and modelling assumptions. Comparisons should therefore use consistent experimental conditions and clearly documented metrics.
